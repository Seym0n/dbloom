# Wave 4 - Settings classification: authentication, sessions, accounts

Status: review input for OPEN.md item 18. Everything marked PROPOSED is a suggestion of the reviewing engineer, not an owner decision. Numeric values come from general security practice (OWASP ASVS/Cheat Sheets, NIST SP 800-63B as remembered); **no live lookup was done, values are unverified** and must be checked before approval.

Basis read: README, 10-conflicts (CF-003/004/005/009/010/011), OPEN 17/18, FUTURE (FU-003), 11-target-security sections 2, 3, 5, 11-14, legacy `01-configuration.md`, `05-security-auth.md` (FR-SAU-200..203, SEC-SAU-201/206/207) and legacy defaults in `libraries/config.default.php` (LoginCookieValidity 1440, LoginCookieStore 0, LoginCookieRecall true, LoginCookieDeleteAll true, CookieSameSite Strict, AllowRoot true, AllowNoPassword false, Captcha keys empty).

Notation: **ENV** = deployment, `.env`, restart. **UI** = administrator UI (account mode only). **UI/ENV-band** = value edited in UI, clamped to a floor and/or ceiling that is set in `.env`. **FIXED** = not a setting, constant in code (listed so nobody builds a switch for it). Direct mode: no UI, so every setting that exists there is ENV.

## 0. Cross-cutting rules proposed by this review

- **R1 Clamp on read.** Effective value = clamp(stored UI value, ENV floor, ENV ceiling), evaluated on every read, not only on write. Reason: if the owner tightens `.env` later, or the store is restored from an old backup, a looser stored value must not survive. Clamping is audited once per change ("clamped by deployment limit").
- **R2 Safe default lives in ENV.** Before the store exists (first start), when a key is missing, or when the store is unreadable, the effective value is the ENV default, and ENV defaults must be the safe values. The store never needs to be readable to apply the safest policy.
- **R3 Loosen is harder than tighten.** SEC-TGT-142 is titled "tighten only" but its text allows any move inside the band. Proposed: tightening needs normal confirmation; loosening (inside the band) needs step-up and takes effect after a cooling-off period (PROPOSED default 24 h, ENV-set, 0 = immediate), shown as "pending" in the UI and cancellable. Limits the damage of a hijacked administrator session and costs a non-technical admin little because loosening is rare. Needs owner decision.
- **R4 Administrator cannot switch off their own safety net.** Step-up, auto-revert, audit, last-administrator protection and the CLI reset are FIXED or ENV, never UI.
- **R5 Administrator 2FA is unconditional (gap in spec).** Step-up (SEC-TGT-143) means "fresh passkey/2FA", but 2FA is only enforceable by policy (SEC-TGT-014). If the policy is "none" an administrator has no factor and step-up is impossible. Proposed: accounts with the administrator role always require 2FA (FIXED); the policy setting governs other roles only. Until the first administrator has enrolled a factor, security settings are read-only and ENV defaults apply.
- **R6 Auto-revert scope.** Besides network lists (SEC-TGT-144), auto-revert with confirmation by a fresh login in a new session should cover: 2FA enforcement scope, allowed factors, rate-limit values, and session lifetimes shortened below a threshold. Reason: these can lock everyone out just as an IP list can.
- **R7 Config fingerprint.** For multi-instance deployments, each instance publishes a hash of its security-relevant ENV values to the store; an instance that sees a different hash logs a warning and shows it on the admin page (PROPOSED: refuse to start for the "must agree" keys marked below).
- **R8 Where the UI bounds live.** One ENV pair per UI setting: `<NAME>_MIN`/`<NAME>_MAX` plus `<NAME>_DEFAULT`. Names below are illustrative.

## 3. Disagreements with, and gaps in, the spec text

- **D1 "Tighten only" vs the text (SEC-TGT-142, section 14 title).** The rule says tighten only, but its test ("UI may move a setting within those limits") allows loosening inside the band. Needs a decision: either true one-way tightening (loosening only via ENV/restart), or the asymmetric rule R3 proposed here.
- **D2 Administrator 2FA not guaranteed (SEC-TGT-143 vs SEC-TGT-014).** Step-up requires a fresh passkey/2FA; 2FA enforcement is policy only. Needs R5 (administrators always have 2FA) or a password re-entry fallback for step-up.
- **D3 Recovery and invite links give a hijacked administrator full account takeover (FR-TGT-104/105).** Only the vault is protected. Spec should state what recovery resets (AS-74), that the user gets a notice, and that role-bearing invites (especially for administrator) need step-up. Also consider second confirmation by another admin for creating an administrator invite, although four-eyes for settings was excluded.
- **D4 SEC-TGT-012 / 015 / 017 leave values open.** They say "configurable" without bounds; this file proposes bounds, none of which exists in the spec yet. SEC-TGT-017 says "exponential backoff"; hard lockout is not wanted (AS-63).
- **D5 SEC-TGT-041 "both shall be configurable"** does not say where; here: UI in account mode with ENV band, ENV in direct mode. Per-role (administrator) values are new.
- **D6 SEC-TGT-011 "check sign count"** breaks synced passkeys that always report 0; refine to the 0/0 rule (AS-20).
- **D7 SEC-TGT-026 vault.** Spec has no vault auto-lock (AS-83), no vault passphrase policy (AS-81), no KDF parameter source (AS-80); and the vault key sits in server session memory, which conflicts with multi-instance unless sessions are sticky or encrypted in a shared store (AS-50).
- **D8 SEC-TGT-040 `__Host-` prefix.** Cookies with this prefix are per host and not per port, so two instances on one host collide, and sub-path hosting is excluded (already open in SEC-TGT-135).
- **D9 Direct mode.** FR-TGT-141 (admin UI) does not apply, so rate limiting, session lifetimes, cookie attributes and AS-90/91 are ENV-only there; 2FA, passkeys, invites, vault, concurrency, notices and step-up do not exist. SEC-TGT-018 says direct mode "shall still meet SEC-TGT-020 to 023, 030 to 033 and 040 to 043" but not 017 (rate limiting); it should, with the per-target key (AS-64), since DBLoom otherwise is a brute-force proxy against third-party DB servers.
- **D10 FR-TGT-149 notices** need an administrator who is logged in to see them; an unattended deployment never sees them. In-app notice alone is weak with no email (CF-011); an ENV audit sink (AS-97) is the complement.
- **D11 Legacy-feature dispositions missing** for `LoginCookieStore`, `LoginCookieRecall`, `LoginCookieDeleteAll`, `Captcha*`, `AllowNoPassword`, `AllowRoot`, `blowfish_secret`; proposed dispositions in the table (replace/drop/ENV).
- **D12 OPEN 17 "password policy"** includes "minimum length, breached check" only; Argon2 parameters, maximum length, temp-password validity and forbidden composition/expiry rules are also needed (AS-31, 32, 34, 35).

## 4. Open questions for the owner

1. Is a passkey a **primary credential** (passwordless, with user verification) or only a second factor after a password? FR-TGT-104 says "passkey or password" at invite redemption, which suggests primary. This decides AS-12/AS-13 and the stage at which 2FA is required.
2. Adopt R3 (asymmetric loosening with step-up and a cooling-off) and R5 (administrators always have 2FA)? Adopt R6 (auto-revert for auth-related settings)?
3. Is switching the login mode on a deployment with data supported at all? Proposal: the store records the mode and startup refuses a mismatch unless an explicit migration command is run.
4. Should DBLoom offer "remember me" or "remember this device for 2FA"? Proposal: no (AS-46/47).
5. Hard-coded minimums: are these acceptable PROPOSED numbers (password 12, Argon2 19 MiB / t2 floor, vault 64 MiB / t3, TOTP +-1, invite 256 bit)? Please also confirm the runtime has memory for them (stack).
6. Breached-password check source: offline list, online range API, or none? Fail open or closed when unavailable (NFR-TGT-093 says fail closed for security failures)?
7. Should a recovery link also reset second factors (AS-74)? Should administrator invites need a second administrator?
8. Is "deny root" on targets wanted (AS-91), and who owns AS-90/91: this domain or the target-policy domain?
9. Audit retention requirements (legal minimum/maximum) and whether IP addresses may be stored.
10. Are several instances in the first release (Q5 rows)? If yes, session store, rate counters, TOTP replay memory and the setup claim all need a shared store, and OPEN 12/13 (store type) block this domain.
11. Do administrators get separate (shorter) session limits (AS-40/41)?
12. Is the legacy captcha dropped (AS-92)?

## 5. Dependencies on undecided scope or stack

- Store type and sharing (OPEN 12/13): AS-44, 50, 66, TOTP replay, setup claim, audit.
- Stack (OPEN 2): Argon2 and WebAuthn library choice and runtime memory limits (AS-34, 80, 19, 20), cookie/`__Host-` and fragment handling (AS-48, 71), middleware for step-up (SEC-TGT-143).
- Scope (OPEN 1): whether TOTP and recovery codes are in the first release, whether several instances are, whether SSO (SEC-TGT-016) is, which would add an IdP-managed 2FA and change AS-10/12/13/30.
