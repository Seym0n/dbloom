## 1. Objective
A deployment is taken over safely by its operator, never by whoever reaches it first: a one-time token protects a five-step wizard that records the login mode, the site defaults and, in account mode, the first administrator with an enrolled second factor; afterwards the setup routes are gone. In account mode people sign in to DBLoom with their own account (password plus a second factor, or a passkey with user verification alone), are slowed down but never locked out by failures, cannot learn from the login whether an account exists, and recover a lost factor with a recovery code or a link the administrator hands over. After signing in they choose a target from a connection picker, connect with typed credentials kept only in session memory or with a personal profile whose secrets are encrypted in a vault only they can open, hold several connections at once and use one per browser tab. Every user's preferences (theme, language, hidden databases, the module preferences) follow them across browsers. Administrators create users and invites; every account event is audited without secrets.

### SCN-064 First-run setup in account mode (A)
*Actor:* operator. *Before:* empty data directory; token from `.env`.
1. The operator opens `/`, sees the welcome step with the store mode, types a wrong token (same page, one message), then the right one.
2. Step 2 preselects account mode from `.env`. Step 3 shows the prefilled site values and the read-only `.env` status with the public-origin check. Step 4: user name `admin`, a breached password (refused, fail closed), then a good one; enrols a passkey (virtual authenticator with user verification); saves the recovery codes. Step 5 confirms.
*Accept when:* no store row exists before step 5 (store inspected after step 4); six wrong tokens are delayed; after step 5 `/setup` and every setup function return 404, also after a restart; the token file is gone; the console shows "setup token consumed"; the administrator signs in with the passkey alone and lands on the connection picker; audit has `setup.complete` without secrets.
*Requirements:* DEP-TGT-100, 123; ST-031, 050, 051; FR-DEP-045; FR-AUT-001, 002, 003, 005; SCN-001.

### SCN-065 Setup in direct mode, stateless mode, mode mismatch (D, S)

### SCN-066 Password plus TOTP, recovery code, throttling, enumeration (A)
*Before:* user `ana` with password and TOTP; no user `bob`.
1. `ana` signs in with password, enters a TOTP code; signs out; signs in again and reuses the same code inside its 30 s; then uses a recovery code; then the same recovery code again.
2. Six wrong passwords for `ana`, six for `bob`; wrong TOTP five times in one challenge.

## 4. Objective of the module spec in one line
Only the operator can set DBLoom up, only the right person can sign in, nobody learns who has an account, and saved database passwords stay readable by their owner alone.

## 5. Design

### 5.1 Threat assumptions
| Actor | Can | Must not be able to | Main controls |
|---|---|---|---|
| T1 network attacker, unauthenticated | reach `/`, `/setup`, `/invite`, `/recover`, sign-in functions | take over a fresh install, guess passwords or codes, learn which accounts exist, replay a challenge, forge a state change | setup token and its throttle, Argon2id plus backoff per account and address, dummy hash, generic codes, single-use server challenges, CSRF and Fetch-Metadata (skeleton), fragment tokens |
| T2 holder of a stolen session cookie (no factor) | use the session until it ends | add or remove factors, issue invites, switch 2FA off, read the vault without the passphrase, survive a password change | step-up with a factor, `security_version`, vault passphrase, short administrator lifetimes, session list and remote sign-out |
| T3 thief of the store file or a backup | read every table offline | use password hashes cheaply, read TOTP secrets, read profiles, test recovery codes | Argon2id, TOTP and recovery-code material under the server key kept outside the volume (Q2), vault with its own Argon2id, tokens as hashes |
| T4 malicious or hijacked administrator | everything the admin role allows | read a user's vault; take over an account silently | vault independent of all admin actions; recovery revokes factors and creates notices; step-up for admin actions |
| T5 phishing site | relay what a user types | use a passkey on another origin | WebAuthn origin and RP ID checks; TOTP and passwords remain phishable (documented) |
| T6 compromised dependency | run code at install or run time | — (not fully preventable) | exact pins, lock file, `npm audit`, lifecycle scripts off (DEP-TGT-126), few packages (Q1) |

Out of scope: an attacker with code execution or memory access on the DBLoom host (can read unlocked vault keys and the server key), volumetric denial of service (edge components), a compromised browser.

### 5.2 What exists and what changes
The skeleton built direct mode: `DirectAuth.login` (generic error, two `FailureLimiter`s with a fixed block), `SessionManager` (token as SHA-256 in `sessions`, target pool and CSRF token in memory), `sessionMiddleware` (G10 single "session ended"), `sameOriginMiddleware`, `__Host-dbloom-session` cookie (Strict), host policy, `audit()` on stdout. This module: (1) adds the mode switch and setup gate to `runtime.ts` and the start plugin; (2) extends `SessionManager` with account sessions, states and the per-session connection map without changing direct mode; (3) replaces the fixed block in `rate-limit.ts` by the backoff limiter (direct mode keeps its keys); (4) adds `accountMiddleware` and the `x-dbloom-connection` header to `csrfClientMiddleware` and to the raw routes (`api/io/upload`, `api/rows/*`); (5) replaces the three `ownerKeyOf(session.target)` call sites by one `ownerKeyFor(session)`; (6) adds migration 5. The confirmation tokens of `guard/confirm-token.ts` stay as they are (per process); their `sessionId` claim becomes the `scopeKey`.

### 5.3 Flows
```
SETUP    GET /setup -> step 1 token -> setup.verifyToken (throttle, constant time) -> __Host-dbloom-setup
         steps 2..4 in memory (setup.saveStep, setup.passkeyOptions/verify, setup.totpStart/verify) -> setup.complete (tx) -> 404 forever
SIGN-IN  auth.passwordSignIn -> throttle -> verify|dummy -> session(pending_mfa|enrol_only|must_change|full) -> new cookie
         auth.mfaOptions -> challenge -> auth.mfaVerify {passkey|totp|recovery} -> session full, mfa_at, new cookie
         auth.passkeyBegin (__Host-dbloom-pre) -> auth.passkeyFinish (UV required) -> session full
CONNECT  connections.open {profileId | typed} -> rules (FR-AUT-020) -> pool -> connectionId -> tab stores id
TARGET   any target function: sessionMiddleware(session + x-dbloom-connection) -> LiveSession (unchanged contract)
INVITE   invites.issue (admin, step-up) -> link#token ; /invite -> invites.redeem {token, username, password|passkey}
RECOVER  recovery.issue (admin module or CLI) -> link#token ; /recover -> recovery.redeem (tx, ST-085)
VAULT    vault.create / unlock / lock / changePassphrase / useRecoveryKey / rotate ; profiles.* need unlocked key
```

### 5.4 Cryptography (exact)
| Item | Construction | Stored |
|---|---|---|
| Login password | NFKC; Argon2id m 64 MiB, t 3, p 1 (ST-067), salt 16 B, tag 32 B | PHC string |
| Dummy hash | same parameters over a random password at start | memory |
| Setup token | 160 bit random, Crockford base32 | SHA-256 in memory; plain in 0600 file while pending |
| Invite, recovery token | 256 bit random, base64url, URL fragment | SHA-256 |
| Session token | 256 bit random (skeleton) | SHA-256 (skeleton) |
| Pre-auth cookie | 256 bit random, 5 min | SHA-256 in memory |
| Server key | 256 bit from `.env` or file (Q2); HKDF-SHA-256 subkeys | never in the store |
| TOTP secret | 160 bit random; AES-256-GCM under subkey `totp`, AAD `totp/v1/<user id>` | sealed record |
| Recovery code | 60 bit random, 12 base32 characters | HMAC-SHA-256(subkey `recovery-codes`, user id ‖ code) |
| WebAuthn | library; challenge 32 B random per ceremony | credential public key, counter |
| Vault key | 256 bit random | wrapped twice (below) |
| Passphrase wrap | Argon2id m 128 MiB, t 3, p 1 (ST-086; min 64 MiB) → AES-256-GCM, AAD `vault/v1/passphrase/<user id>` | salt, parameters, sealed key |
| Recovery-key wrap | 160 bit random key → HKDF-SHA-256 (salt 16 B, info `vault/v1/recovery`) → AES-256-GCM, AAD `vault/v1/recovery/<user id>` | salt, sealed key |
| Profile secret | AES-256-GCM under the vault key, 12 B nonce per write, AAD `profile/v1/<user id>/<profile id>` | sealed JSON `{user, password, clientKey?}` |

All randomness from `crypto.randomBytes`; all comparisons of secrets with `timingSafeEqual` after equal-length hashing; key buffers are zeroed with `fill(0)` when dropped (best effort in a garbage-collected runtime, documented).

**Key rotation.** Server key: set the new key as `DBLOOM_SECRET_KEY`, the old one as `DBLOOM_SECRET_KEY_PREVIOUS`, restart, run `rotate-secret`, then remove the previous key. Losing the server key makes TOTP secrets and recovery codes unusable (users fall back to passkeys or an administrator recovery link); it does not affect passwords, passkeys or vaults. Vault: passphrase change re-wraps; "rotate vault key" re-encrypts profiles; recovery-key regeneration re-wraps.

### 5.5 Sessions, states and connections
| State | Allowed functions | Next |
|---|---|---|
| `pending_mfa` (5 min) | `auth.mfaOptions`, `auth.mfaVerify`, `auth.signOut` | `full` / `must_change` |
| `enrol_only` | enrolment functions, account security read, `auth.signOut` | `full` after the first factor |
| `must_change` | `account.changePassword`, `auth.signOut` | `pending_mfa` or `full` |
| `full` | everything the role allows | — |

Direct-mode sessions are `kind = direct`, state `full`, no user, one implicit connection (today's behaviour). The connection map lives next to the session runtime (`Map<idHash, {csrf, connections, vaultKey?, vaultSeenAt}>`); on session end all pools close and the vault key is zeroed. Owner key for per-user data: `u:<user id>` (account), `ownerKeyOf(target)` (direct), session id hash (stateless).

### 5.6 Vault and profiles
Profiles can be listed while the vault is locked (plain metadata, Q10); opening one asks for the passphrase in a dialog and keeps the key for ST-089 minutes of vault inactivity (each use of a profile secret counts). A profile connection holds its decrypted password only inside the pool configuration, like typed credentials; locking the vault does not close open connections, but a reconnect (G5) then asks for the passphrase. The vault never feeds the audit log and never leaves the server.

### 5.7 Store (migration 5)
Migration 5 (current is 4): `ALTER TABLE sessions ADD COLUMN` × 8 (section FR-AUT-017; `ADD COLUMN` on a STRICT table, *verify* in spike 0); new STRICT tables `site(key PRIMARY KEY, value)`, `settings(key PRIMARY KEY, value, updated_at, updated_by)`, `users`, `passwords(user_id PRIMARY KEY, phc, changed_at)`, `webauthn_credentials(id PRIMARY KEY, user_id, public_key BLOB, counter, transports, backed_up, uv_initial, name, created_at, last_used_at)`, `totp(user_id PRIMARY KEY, sealed, last_step, created_at)`, `recovery_codes(user_id, code_mac, created_at, PRIMARY KEY(user_id, code_mac))`, `tokens(id PRIMARY KEY, kind CHECK IN ('invite','recovery'), token_hash UNIQUE, user_id, role, created_by, created_at, expires_at, used_at, revoked_at)`, `vaults(user_id PRIMARY KEY, kdf_params, kdf_salt, wrap_passphrase, recovery_salt, wrap_recovery, created_at, updated_at)`, `connection_profiles(id PRIMARY KEY, user_id, name, host, port, tls, options, sealed, created_at, updated_at, last_used_at, UNIQUE(user_id, name))`, `user_notices(id PRIMARY KEY, user_id, kind, created_at, read_at)`; foreign keys `ON DELETE CASCADE` from every user-owned table to `users`. ### 5.10 UI (package E)

## 9. Code style
As file 21 section 6. Handlers stay thin and every security decision lives in one service function with a test:
```ts
export const mfaVerifyFn = createServerFn({ method: 'POST' })
  .middleware([pendingMiddleware])                  // only sessions in state pending_mfa
  .validator(mfaVerifySchema)                       // zod: {method: 'totp'|'passkey'|'recovery', ...}
  .handler(async ({ context, data }) => {
    const challenge = challenges.take(context.session, 'mfa')        // deleted now, success or not
    const ok = await verifyFactor(context.user, challenge, data)     // library errors -> false, detail to log
    if (!ok) throw authError('mfa_failed')                           // one message, stable code
    return completeSignIn(context.session, { mfaAt: Date.now() })    // regenerates the token
  })
```
No secret in an exception message, a log call or a returned object; secret-bearing values are typed `Secret<string>` (a branded wrapper whose `toJSON` and `toString` return `[secret]`) so a slip shows in tests.

## 10. Testing strategy
- Unit: RFC 6238 vectors, TOTP window and replay, PHC encode/parse and rehash, NFKC and length rules, breached lookup, HKDF/seal/open tamper and AAD tests, key rotation, vault wrap/unwrap, code and token formats, throttle with a fake clock, policy and state matrices, settings precedence and clamping, preference registry and import schema, last-admin invariant.
- Integration (store in a temp directory; MySQL 8.4 on 33064 and MariaDB 10.11 on 33061): sign-in flows, enumeration timing, session states and eviction, ST-075 invalidation, connections and isolation, connect rules, profiles with the vault, recovery effects, CLI commands against a running server.
- E2E (Playwright, account-mode web server, Chromium virtual authenticator): SCN-064 to SCN-077; SCN-001 to 004, 009, 010 stay green. Specs that change site settings use their own data directory.
- Security checks: CSRF and Fetch-Metadata on every new function; token replay and tamper; a log scan for every secret the tests create; byte search of the store file for profile plaintext; no setup route after completion; no secret in any response (snapshot of response bodies); timing comparison for unknown users.
- CI as in file 21 section 8; the Node 22 job depends on Q1.

## 11. Boundaries
- **Always:** test first for crypto, policies and state machines; one generic error per failure class; constant-time comparisons; regenerate the session token at every state change; audit every account event without secrets; reuse host policy, `normaliseTarget`, `audit()`, CSRF and the preference table; `t()` for text; the two design skills for every screen; lint, typecheck, unit and the touched e2e before reporting done.
- **Ask first:** any dependency beyond Q1; changing the meaning of a skeleton table; changing the session cookie; adding a role; any outbound call; changing a fixed-in-code setting of section 5.8; any commit or push.
- **Never:** store or log a password, passphrase, recovery key, code, token, TOTP secret or target credential in plain text; put a secret in a cookie, URL query, local storage or response after its one-time display; reveal whether an account exists; lock an account permanently; let an administrator or the server key open a vault; accept a WebAuthn response without a held challenge; fall back to a weaker hash or library when one is missing (DEP-TGT-091); send email.

## 12. Success criteria
1. SCN-064 to SCN-077 pass on MySQL 8.4 and MariaDB 10.11; SCN-001 to 004, 009, 010 still pass.
2. A fresh deployment cannot be used before setup and cannot be set up without the token; after setup no setup route exists.
3. No test can distinguish an unknown user from a wrong password by message, status or (statistically) timing; no account is ever locked permanently.
4. Replay of every challenge and code fails; a stolen session cannot change factors or issue invites without a fresh factor.
5. The store file contains no plaintext secret of the test run; the vault opens only with passphrase or recovery key.
6. 50 parallel sign-ins keep memory bounded (FR-AUT-005) and the median sign-in stays under 1 s on the CI runner (*verify* Argon2 timing in spike 0).
7. Lint, typecheck, unit, integration and e2e green in CI; axe clean on every new page.
