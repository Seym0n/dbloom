## 0. Assumptions (correct me now)
1. Direct mode, one target per session, as in the skeleton. Stateful mode has the SQLite store (default); stateless mode (`DBLOOM_STORE=none`) has no store: display preferences then live in the session or in browser storage (only non-sensitive layout, section 5.9). Account mode is not built yet; the new store table is keyed like the SQL state (section 5.9).
2. First slice = everything that touches the rows of one base table in the table tab: page, multi-column sort, counts, filter builder, search, column display options, cell viewer (long text, whitespace, hex, JSON, geometry as text), binary download and upload, foreign key links and pickers, insert (several rows, copy), edit inline and in a form, delete, bulk delete and bulk edit of selected rows, the guard, the SQL preview, audit. Deferred or other modules: section 2.4 and 2.5.
3. The write guard pieces exist and are reused unchanged: `assertWritable(GuardContext)`, `createTokenIssuer` / `hashStatements` / `StatementClass`, `runWithTimeout` (buffered), `audit`, `mapMysqlError`, `PlanStore`, `strategyFor` / capability probe, `quoteIdent`, `resolveTable`. Four additive edits to them are listed in task 0 (section 13); everything else lives in new folders (`src/server/rows/`, `src/lib/rows/`, `src/components/rows/`).
4. The row editor works on one base table in the table tab. Results of the SQL tab stay read-only in this slice (FR-ROW-032); DATA-ISS-110 is met by construction (edit actions exist only where an identity exists).
5. Values are bound as parameters on server-side prepared statements (`pool.execute`), never interpolated by DBLoom and not by the driver's client-side escaper either (reason in section 5.1: `NO_BACKSLASH_ESCAPES`). Reads that need the text protocol are listed in section 5.3.
6. No new dependency is needed: native inputs, `Intl`, the existing shadcn base components, `@tanstack/react-query` and the existing `zod`. A virtualised grid is not needed (page size at most 1 000).
7. The target's privileges are the security boundary (SEC-TGT-050). The guard, the classes and the filter allow-lists are guard rails and are documented and tested as such.

## 1. Objective
A permitted user can open a table, find the rows they need (structured filter, quick search, sort, paging, an honest row count), look at any value without risk (long text, binary, JSON, geometry, whitespace shown visibly), follow foreign keys, and change data: insert rows (also copies of rows), edit a cell or a whole row, delete one or many rows. DBLoom identifies each row by its primary key, else a unique key, else (after a per-edit confirmation) by an exact match on all columns with `LIMIT 1`; writes only the values the user changed, so opening a row and saving it without changes never alters stored data; checks that the row was not changed by someone else meanwhile; shows the exact SQL before it runs; asks for a server-checked confirmation for destructive changes; refuses everything on a read-only connection; audits each change without values; and shows the server's own error when it fails. All SQL comes from one typed builder with parameters; the browser never sends SQL, WHERE text, ORDER text or LIMIT text.

### 2.5 Column transformations (FR-PLG-*, owner decision 2026-10-23): decision of this draft
The owner adopted the feature; this draft does not build it in the first slice of `rows`, and gives it its own later module `transformations`. Reasons: (1) it needs persistent per-column configuration (MIME type, transformation, options) that must live in the DBLoom store, not in the target (no `la_column_info`), with its own migration, cascade cleanup on drop and an editor screen; (2) it is a registry of about 25 built-in display and input behaviours plus a signed-address endpoint, which is a feature of its own size, and the closed built-in registry (FU-006) must be designed once; (3) the two things users need on day one are not transformations but fixed viewers that rows ships anyway: long text, whitespace, hex, JSON pretty, image and PDF preview, download, upload (FR-ROW-011 to 013); (4) postponing costs no rework because FR-ROW-031 defines the seam now: the grid renders a cell through `renderCell(kind, cell, options)` and the form edits a value through `ValueEditor(kind, ...)`, each looked up in a registry that has only the built-in entries; `transformations` adds registry entries and one store table. The 24 `FR-PLG-*` rows, `CPT-PLG-006`, `DATA-DEP-066`, `DATA-PLG-002`, `DATA-PLG-008`, `FR-DTB-137`, `NFR-PLG-004`, `SEC-PLG-007`, `SEC-PLG-008` therefore read DEFER above.

## 4. Objective of the module spec in one line
The user finds rows with a safe structured filter, sees every value truthfully, and changes rows through one parameterised builder that identifies the row, checks for concurrent changes, shows the SQL and asks the server for confirmation where data is lost.

## 5. Design

### 5.1 Data flow and the one builder
```
client (typed data only) -> zod strict -> session + CSRF -> assertWritable (writes) -> loadRowTable (catalog model, SEC-TGT-116)
  -> identityFor -> codec (validate, encode) -> builder (sql + params + preview) -> classify (rows/classes.ts)
  -> none: run | soft/hard: PlanStore + token -> run (one connection, transaction, runWithTimeout) -> re-read -> audit -> response
```
`src/server/rows/builder.ts` exposes pure functions that return `BuiltStatement = {sql: string, params: unknown[], preview: string, kind: 'rowInsert'|'rowUpdate'|'rowDelete'|'rowSelect', effect: string}`: `buildPage`, `buildCount`, `buildRowByIdentity`, `buildLookup` (FK display values), `buildInsert`, `buildUpdate`, `buildDelete`, `buildCellRead`. Each takes the `RowTable` model and already-encoded values; none takes a string that came from the client other than through the model (column names) and the codec (values). Why `execute` and not `query` with `?`: the driver's `query` fills `?` on the client with its escaper, which uses backslash escapes; with `sql_mode` containing `NO_BACKSLASH_ESCAPES` a value ending in a backslash or containing `\'` is no longer safe. `execute` sends the values in the binary protocol, so the server never parses them as SQL. Observed in spike 0b on both products: `execute` returns FLOAT through the binary protocol as the 32-bit value widened to a double (`0.10000000149011612` for `0.1`), hence the `CAST(col AS CHAR)` projection for float kinds (5.3); `dateStrings`, `bigNumberStrings` and `jsonStrings` behave the same on the binary and the text protocol (DATETIME(6), TIME(3), BIGINT, DECIMAL(30,10) identical); with `NO_BACKSLASH_ESCAPES` set, the value `x\' OR 1=1 -- \` stored correctly through `execute` and broke the statement through `query` with `?` (syntax error 1064), which confirms Q1; `LIMIT ?` works through `execute` but the builder still prints validated integers; `execute` caches prepared statements per connection with mysql2's default `maxPreparedStatements` of 16 000 while the server allows 16 382 in total (`max_prepared_stmt_count`), so the target pool must set `maxPreparedStatements` to a small number (about 100) when this module is built (a one-line additive change of `openTargetPool`, announced to the skeleton owner).

The statement text for one table is stable for a given set of columns, which makes the server's statement cache useful; the preview is built from the same pieces and is the only place that substitutes values (display escaping only).

### 5.3 Value codec per type kind (read projection / write form)
| Kind | Read (SELECT list) | Write | Notes |
|---|---|---|---|
| `int` (incl. `BIGINT`) | column as is; driver returns strings for big numbers | `?` with decimal string; `0x` form converted | range check by `unsigned` and width |
| `decimal` | as is (string) | `?` string | validated against precision and scale; never a JS number |
| `float`, `double` | `CAST(col AS CHAR)` (so the binary protocol cannot show 0.10000000149011612) | `?` text | no old-value compare by `=`; digest compare (FR-ROW-005) |
| `bit(n)` | `LPAD(BIN(col+0), n, '0')` | a big-endian `Buffer` of `ceil(n/8)` bytes as the parameter (the value of `b'...'`) | observed, spike 0b: the driver returns BIT as a Buffer, hence the projection; `CAST(? AS UNSIGNED)` fails on MySQL 8.4 above 2^63 (error 1292), so it is not used; a Buffer works up to `BIT(64)` on both products |
| `date`, `time`, `datetime`, `timestamp`, `year` | as is with `dateStrings` | `?` string, strict syntax check, fractional part kept | `0000-00-00` shown as is; `sql_mode` decides acceptance |
| `char`, `text`, `enum`, `set` | as is, cut at `cellBytes` | `?` string verbatim; `SET` comma-joined, empty allowed | no trim, no newline normalisation |
| `binary`, `blob` | `SUBSTRING(col, 1, 32)` and `OCTET_LENGTH(col)` in the grid projection; full bytes only through `openCell` / `readCell` | `?` Buffer or `uploadId` bytes | `BINARY(n)` padding preserved; hex input padded only if the user asks |
| `json` | as is (`jsonStrings`) | `?` as text on both (MySQL also accepts `CAST(? AS JSON)`; MariaDB does not) | digest compare on the text; MySQL stores JSON normalised (`{"a": 1, "b": 2}`, keys sorted), MariaDB keeps the text as written, so the digest is always taken from the value read back (observed, spike 0b) |
| `geometry` | `ST_AsText(col)`, `ST_SRID(col)` | `ST_GeomFromText(?, ?)` | no old-value `=`; digest compare `SHA2(ST_AsBinary(col),256)` works on both (observed, spike 0b) |
| `uuid`, `inet6` (MariaDB) | as is | `?` string | capability key `type-uuid` / `type-inet6` |
| `unknown` | `CAST(col AS CHAR)` | never written | message shown (DATA-ISS-118) |
The grid projection for large columns is `LEFT(col, cellBytes+1)` for character kinds so a 1 GB `LONGTEXT` does not cross the wire, with the length from `CHAR_LENGTH(col)` computed in the same statement only for columns shown in full-text mode (cost observed 2026-10-26, five rows of one `LONGTEXT` each, utf8mb4 text with 2- and 4-byte characters, `query` through mysql2, mean of 5 runs: MySQL 8.4 with 32 MiB per value: full `SELECT` 1 315 ms and 84 MB over the wire, `LEFT(c, 65537)` 259 ms and 0.4 MB, plus `CHAR_LENGTH(c)` 427 ms, plus `OCTET_LENGTH(c)` 213 ms; MariaDB 10.11 with 8 MiB per value: full 256 ms and 21 MB, `LEFT` 6.8 ms, plus `CHAR_LENGTH` 38 ms, plus `OCTET_LENGTH` 7.4 ms. So `LEFT` removes the transfer cost, `OCTET_LENGTH` is nearly free because it reads the stored length, and `CHAR_LENGTH` on multi-byte text must scan the whole value (about 1.6 times the `LEFT`-only cost on MySQL, 5 times on MariaDB). The first implementation selects `CHAR_LENGTH` for every character column (`lengths` option of the projection in `codecs.ts`, default true), so a table with very large text columns pays that scan on every page; follow-up: derive the truncation mark from the length of the `LEFT` result and show the byte length from `OCTET_LENGTH`, or select `CHAR_LENGTH` only for columns in full-text mode as first planned).

### 5.4 Row identity, old values and writes
Identity per FR-ROW-004. Update statement shape for a keyed row: ``UPDATE `db`.`t` SET `c1` = ?, `c2` = ? WHERE `id` = ? AND `c1` <=> ? AND BINARY `c2` <=> BINARY ?`` (illustrative; the real text follows the table in 5.3 per kind); `LIMIT 1` is added for `all-columns` and omitted for keyed rows (the key bounds the match; adding it would hide a duplicated-key anomaly of a non-unique key). Delete shape the same without `SET`. Insert: ``INSERT [IGNORE] INTO `db`.`t` (`c1`, `c2`) VALUES (?, ?)`` with `DEFAULT` written as the keyword for default-valued fields (fixed token, not a parameter) and function values from the fixed template (`NOW()`); an insert with no field set is ``INSERT INTO `db`.`t` () VALUES ()``. After a write the row is re-read with `buildRowByIdentity` using the new key (insert id from the driver for auto-increment, else the key the user typed).

| binary, blob | `=`, `!=`, `in`, `is null`, `is not null`, `starts with (hex)` | `?` as Buffer from the hex value; `starts with` as `` LEFT(`c`, n) = ? `` |

Groups compile to parenthesised `AND`/`OR`, `negate` to `NOT (...)`. Operators and the compile are table-driven so the allow-list is data, reviewable in one place. The advanced expression field (Q5), if approved, reuses `structure/expression.ts` plus the parser facts of `sql/parser.ts` and is outside this table.

### 5.6 Classes, confirmation, plan store
`rows/classes.ts` maps a `RowChange` plus the `RowTable` to a class and a list of reasons (`no-key`, `bulk`, `cascade`, `no-rollback`, `delete`, `engine-nontransactional`) as in FR-ROW-020. Reuses `PlanStore.create(sessionId, {statements, warnings, statementsHash, db, table, payload})` with `payload` holding the encoded `RowChange` and uploads' SHA-256; `Statement` gets an optional `params` array (additive) and `hashStatements` includes the canonical JSON of `params` in the hash when present, so a token binds to the exact values, not only to the SQL shape. `changeRows` / `confirmRows` are the two server functions of the flow; the first returns `done | confirm | conflict | gone | error`. Soft confirmations honour `acceptSoft`; hard cannot be switched off. A plan that was built from a row version (`old` values) is not refreshed on confirm: if the row changed between plan and confirm, the conflict check fails normally.

## 11. Boundaries
- **Always:** one builder; parameters for every value; names only from the catalog model and `quoteIdent`; write only changed columns; old-value check on every update and delete; `assertWritable` first; class computed on the server; one transaction for multi-statement changes; show the preview; audit without values; table-driven tests first for builder, codec, filter and classes; run lint, typecheck and tests before reporting done.
- **Ask first:** adding a dependency, widening the filter allow-list, changing the class thresholds of FR-ROW-020, changing `Statement`, `StoredPlan`, `hashStatements`, `StatementKind`, `statement-timeout.ts`, the audit line format or the migration runner beyond the stated additions, enabling the advanced expression field, bulk operations on "all matching", editing results of the SQL tab, any commit or push.

FOR UPDATE` held across requests; replay a write automatically after a dropped connection; weaken the read-only guard.

## 12. Success criteria
1. SCN-037 to SCN-051 pass on MySQL 8.4 and MariaDB 10.11.
2. No statement of the module contains a value; the no-literal property test and the lint rule are green; hostile values and column names change nothing.
3. Opening a row for edit and saving without changes sends nothing, and changing one field changes only that field, for every type in the round-trip suite.
4. A delete of several rows, a write by `all-columns` identity and a cascade-affected write never run without a valid, single-use, plan-bound token; a tampered or reused token never runs one.
