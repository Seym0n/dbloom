# 11 — DBLoom Target Security Requirements (proposed)

Unlike files 00–09, this file does **not** describe LegacyAdmin 5.2.3. It proposes security requirements for **DBLoom**, each traced to the legacy gap or behaviour it replaces. It complements `10-conflicts.md`.

## Status and basis
- **Status: PROPOSED.** Written by the reviewing engineer from general security knowledge. Not yet approved by the project owner, and **not verified against current standards documents** (no live lookup was done). Requirements that depend on an open decision say so.
- **ID scheme:** `TYPE-TGT-NNN`; `TGT` = DBLoom target design (new subsystem code, to be added to the README table). Types follow the README (SEC, FR, NFR, DEP, DATA).
- **Baseline:** OWASP ASVS Level 2 is proposed as the verification baseline (TGT-SEC-001).
- **Legacy references** use IDs from `05-security-auth.md` (SAU), `02-server.md` (SRV), `03-database-table.md` (DTB) and the conflicts `CF-nnn` from `10-conflicts.md`.
- **Threat context:** DBLoom holds or handles login credentials for many database servers and can be directed at arbitrary hosts. It is a high-value target and a potential SSRF pivot (CF-001, CF-006).

---

## 1. Baseline and process

- **SEC-TGT-001** — DBLoom shall be verified against OWASP ASVS Level 2; every SEC requirement in this file shall have at least one automated or documented test. *Replaces:* no legacy equivalent.
- **SEC-TGT-002** — A written threat model shall exist and be kept current, covering at least: authentication, session, CSRF, XSS, SQL injection, SSRF/arbitrary target connections, file import/export, 2FA, and credential storage. *Legacy basis:* the threat table in `05-security-auth.md` §12.1.

## 2. Authentication to DBLoom

*Login modes decided in CF-009: account mode (two-step) and direct mode (legacy style). Requirements in this section marked "account mode" do not apply in direct mode.*

- **SEC-TGT-010** — In **account mode** (decision CF-009), authentication to DBLoom and connection to a target database server shall be separate steps. Possessing a DBLoom session shall not by itself grant access to any target server, and one session may hold several target connections. *Replaces:* legacy cookie auth, where login is the database login.
- **SEC-TGT-018** — DBLoom shall also provide a **direct mode** (decision CF-009), in which the login page takes server, username and password and no DBLoom account exists, as in LegacyAdmin. Direct mode shall be enabled by an explicit administrator setting, shall show a warning that DBLoom-level protections (enforced 2FA, saved profiles, DBLoom audit identity) are unavailable, and shall still meet SEC-TGT-017, 020 to 023, 030 to 033, 040 to 043 and 131. Rate limiting shall be keyed by effective client address and by normalised target host and username, so that DBLoom cannot be used to guess passwords of third-party servers. Free-form targets in direct mode shall require a named target allow-list or an explicit acknowledgement setting; otherwise startup is refused. A mandatory allow-list is not required in account mode. *(changed, owner decisions D-06)*
- **SEC-TGT-019** — The login mode shall be a deployment setting, and exactly one mode shall be active per deployment (decision CF-009). Neither a per-user mode choice nor both modes at once shall be offered. Recommended default: account mode. The active mode shall be unambiguous on the login page. The store records the mode; startup shall refuse a mismatch between the configured mode and the mode of the store unless an explicit migration command is run. *(changed, owner decisions D-22)*
- **DATA-TGT-094** — In direct mode, preferences, history, bookmarks and layouts shall be kept in a DBLoom-owned store, keyed by target server and username (decision CF-009; interpretation to be confirmed). The key shall use one normalised form of the target (host and port), state of one key shall never be readable under another, and the store shall be written without any privileges on the target server. *Open:* the normalisation rule and whether the store is a file or a database. *Replaces:* the `la_*` tables on the target server and the session-only fallback (CF-001, CF-008).
- **SEC-TGT-011** — Passkeys (WebAuthn) shall be supported as an authentication factor, using a maintained library. Registration and assertion verification shall check signature, origin, RP ID and sign count, and shall fail closed. *Replaces:* the `CustomServer` fallback that skips signature and sign-count checks (FR-SAU-210, FR-SAU-059; CF-004). Sign-count check: a received counter that is not greater than the stored one shall be rejected and audited, except when both are 0 (authenticators that do not count). No attestation is requested (policy `none`). Passkeys are in the first release (owner decision D-08). A passkey can be used as a primary credential (passwordless login) as well as a second factor (owner decision D-08, second half). Consequences: a user may log in with a passkey alone; recovery of a user who lost every passkey follows FR-TGT-105 (a new invite-style link resets the second factors, and the user enrols a new passkey), so users should be encouraged to register more than one passkey (*proposed detail*). A passkey login with user verification satisfies the enforced-2FA policy on its own (owner decision D-08, see SEC-TGT-014). *(changed, owner decisions D-23, D-08)*
- **SEC-TGT-012** — TOTP shall be supported in the first release (owner decision D-08) as an alternative second factor to passkeys, with a verification window of ±1 time step, an accepted code shall not be accepted a second time, and attempts shall be rate-limited. *Replaces:* ±8 steps (SEC-SAU-325; CF-005).
- **SEC-TGT-013** — One-time recovery codes shall be issued at 2FA enrolment, stored only as hashes, and invalidated on use.
- **SEC-TGT-014** — An administrator policy shall be able to require 2FA for all users or for selected roles. *Replaces:* opt-in only, no enforcement (FR-SAU-209; CF-003). Accounts with the administrator role shall always require 2FA; the policy applies to other roles. The first administrator shall enrol a factor before setup completes. A login with a passkey satisfies the 2FA requirement by itself if and only if the authenticator reports user verification (PIN or biometric) in that assertion (owner decision D-08); DBLoom shall request user verification as required for passkey logins and step-up confirmations, and shall reject an assertion in which the user-verified flag is not set. Password login still requires a second factor (a passkey or TOTP). A passkey that cannot do user verification cannot be used for passwordless login, only as a second factor after a password. Not applicable in direct mode. *Verification:* a passkey assertion without the user-verified flag is rejected for passwordless login; a verified assertion alone completes login for an account that requires 2FA; a password alone does not. *(changed, owner decisions D-07, D-08)*
- **SEC-TGT-015** — If DBLoom keeps local passwords, they shall be hashed with Argon2id (parameters configurable) and error messages at login shall not reveal whether the account exists. Hard-coded minimums (PROPOSED, numbers unverified; to be checked against the runtime once the stack is chosen): password length 12, Argon2id for login passwords at least m 19 MiB, t 2, p 1. Passwords shall be checked against an offline breached-password list: fail closed for the first administrator, fail open with a warning otherwise. *(changed, owner decisions D-09, D-10)*
- **SEC-TGT-016** — Where an organisation uses single sign-on, OpenID Connect shall be supported as an alternative to local passwords. *Open:* whether SSO is in scope.
- **SEC-TGT-017** — Login attempts shall be rate-limited per account and per source address with exponential backoff, and repeated failures shall be logged. Throttling shall delay with backoff and shall never lock an account permanently. Thresholds are administrator settings within `.env` bounds (`12-settings.md` ST-076 to 078); in direct mode they come from `.env`. *Replaces:* no brute-force protection in legacy (SEC-SAU-206). *(changed, owner decisions D-06)*

## 3. Target-server credentials

- **SEC-TGT-020** — By default, DBLoom shall not persist target-server passwords. They shall be held only in server-side session memory, encrypted, and discarded at logout or session expiry.
- **SEC-TGT-021** — Target-server credentials shall never be placed in a client-side cookie, URL or local browser storage. *Replaces:* legacy cookie authentication, where the encrypted credentials travel in a cookie (FR-DEP-055, `AuthenticationCookie.php`).
- **SEC-TGT-022** — If saved connection profiles are supported (open decision, CF-006), stored target credentials (username and password) shall be encrypted with authenticated encryption (AEAD, e.g. libsodium or AES-GCM), with associated data binding each record to its profile and owner. They shall never be stored in plain text, and not merely hashed, because they must be reversible. The keys protecting them are specified in SEC-TGT-026 (personal profiles) and SEC-TGT-027 (shared profiles).
- **SEC-TGT-024** — In account mode DBLoom shall support three credential sources for target servers (decision CF-010): (A) credentials entered by the user per connection and kept only in server-side session memory; (B) personal profiles saved per user, encrypted per SEC-TGT-022; (C) administrator-defined shared profiles with a service account. In the first release only (A) and (B) are provided; (C) is deferred (`FUTURE.md` FU-005). Short-lived credentials from a secrets manager or cloud IAM are deferred.
- **SEC-TGT-025** — *(Deferred to the future with shared profiles, FUTURE.md FU-005; not part of the first release.)* For shared profiles (C), the password shall be stored encrypted per SEC-TGT-022, shall never be returned to any user or written to any log, and access shall be limited by DBLoom roles. Every connection through a shared profile shall be attributed in the audit log to the DBLoom user, because the target database sees only the service account (NFR-TGT-090). Service accounts should have least privilege (SEC-TGT-053).
- **SEC-TGT-026** — Personal profiles (option B) shall be protected by a per-user **vault** (decision CF-010; unlock methods interpreted from the owner's answer, to be confirmed): a random vault key encrypts the user's saved credentials; the vault key is locked (1) by a key derived with Argon2id from a **vault passphrase** chosen by the user, which is separate from the login password or passkey, and (2) by a one-time **recovery key** shown once at vault creation. Passphrase and recovery key shall never be stored. The unlocked vault key shall be held only in server-side session memory and discarded at logout or session expiry. Changing the passphrase shall re-lock the same vault key without re-encrypting the profiles. A login password change, a passkey change or an administrator recovery link shall not affect the vault (FR-TGT-105). Without passphrase and recovery key the profiles are unrecoverable, and no administrator shall be able to read them. Unlocking the vault with a passkey (WebAuthn PRF) is a possible later addition and is not required. Vault key derivation minimum (PROPOSED, unverified): Argon2id m 64 MiB, t 3, p 1; vault passphrase minimum 12 characters. *(changed, owner decisions D-09)*
- **SEC-TGT-027** — *(Deferred to the future, FUTURE.md FU-005; not part of the first release.)* Shared profiles (option C) shall be encrypted with a random record key per profile, locked by a **master key** that is held outside the DBLoom store and never written to the store, backups or logs. Rotating the master key shall only re-lock the record keys. DBLoom shall refuse to start when shared profiles exist and the master key is missing or a placeholder (SEC-TGT-081). When introduced, the master key is assumed to be a single symmetric key, with wrapping and unwrapping behind a small interface; key-holder and public/private key variants are further future ideas (`FUTURE.md` FU-001, FU-002). *Open:* where the master key comes from (environment, key file, secret manager, KMS, or entered at startup) (`OPEN.md` item 14).
- **SEC-TGT-023** — Credentials, tokens and recovery codes shall never appear in logs, error messages or audit records. Exception: the one-time setup token may be printed to the console while setup is pending (DEP-TGT-100, decision option 2).

## 4. Connecting to arbitrary servers

*Applies if DBLoom allows free-form target connections, as in the owner's scenario (CF-001, CF-006).*

- **SEC-TGT-030** — Target hosts and ports shall be restricted by a configurable allow-list or deny-list policy. The default shall deny loopback, link-local (including cloud metadata addresses such as 169.254.169.254) and, unless enabled, private ranges. Loopback, link-local, unspecified, multicast and reserved classes and their mapped forms are blocked by `.env` only; private ranges are permitted only if `.env` allows, and the UI may then narrow to named ranges. Allow/deny entries and ports are administrator settings inside an `.env` envelope. Unix-socket targets are not supported in the first release. *(changed, owner decisions D-06, D-17)*
- **SEC-TGT-031** — The target host name shall be resolved once per connection attempt and the connection made to that resolved address, to prevent DNS rebinding. Every returned address shall be validated against the blocked classes before connecting, in normalised form (mapped IPv6, decimal, octal and hex spellings), again on every reconnect; the certificate shall be verified against the host name, not the pinned address. *(changed, owner decisions D-01 to D-23 accepted; see `reviews/wave5-apply-settings-decisions.md`)*
- **SEC-TGT-032** — TLS to target servers shall be enabled and certificates verified by default. Disabling verification shall require that `.env` permits it (default: not permitted) and an explicit per-connection or per-profile choice by the user, which is visible in the UI and audited. *(changed, owner decisions D-01 to D-23 accepted, C-17)*
- **SEC-TGT-033** — Connect timeout and query timeout shall be configurable with safe defaults, and the user shall be told when a limit was hit.

## 5. Sessions and requests

- **SEC-TGT-040** — Sessions shall be server-side. The session cookie shall be `HttpOnly`, `Secure` and `SameSite` (Lax or Strict), use the `__Host-` prefix, and be regenerated at login and at privilege change.
- **SEC-TGT-041** — Both an idle timeout and an absolute lifetime shall apply, and both shall be configurable. *Replaces:* legacy `LoginCookieValidity`-based behaviour (see 05-security-auth.md).
- **SEC-TGT-042** — Every state-changing request, regardless of HTTP method, shall be protected by a CSRF token or an equivalent same-site mechanism; state shall never change on GET. *Replaces:* CSRF checked only for POST (SEC-SAU-324).
- **SEC-TGT-043** — Responses shall carry a strict Content-Security-Policy using nonces (no inline script, no `eval`), `X-Content-Type-Options`, `Referrer-Policy`, frame protection and HSTS where served over HTTPS. *Legacy basis:* header set in SEC-SAU-071/077/078.

## 6. SQL handling and database access

- **SEC-TGT-050** — Because DBLoom must execute SQL typed by the user, the security boundary shall be the target database's privileges, not input filtering. Documentation and tests shall state this explicitly.
- **SEC-TGT-051** — All SQL that DBLoom builds itself shall use parameterised queries for values and one central, tested function for identifier quoting. Fields such as sort columns and log names shall be validated against allow-lists. *Replaces:* unvalidated concatenation (binlog `log` — SEC-SAU-319; ZoomSearch `maxPlotLimit` — SEC-SAU-320; process-list `sort_order` — SEC-SAU-323).
- **SEC-TGT-052** — DBLoom shall offer a read-only connection mode at three levels: forced for the deployment (`.env`); default for new connections (read-only by default, an administrator setting within `.env` bounds); and per connection (any user may tighten, and may switch to read-write unless the deployment forces read-only or policy forbids). It is a guard rail and not a security boundary (SEC-TGT-050) and shall block read-write transaction switches and multi-statement bypass. The destructive-statement confirmation shall be enforced on the server by a two-step token, with the hard class set in `.env` and not switchable from the UI or by users. *(changed, owner decisions D-15)* DBLoom shall also offer a statement timeout, a maximum result size and confirmation before destructive statements (drop, truncate, delete or update without a restricting condition).
- **SEC-TGT-053** — DBLoom shall document the minimum privileges needed per feature so that least-privilege accounts can be used.

## 7. Authorisation

- **SEC-TGT-060** — Authorisation shall be deny-by-default and enforced in one place for every route and action, not only by the target database. *Replaces:* no router-level authorisation (SEC-SAU-321).
- **SEC-TGT-061** — DBLoom roles shall be defined for DBLoom-level functions (managing profiles, enforcing 2FA, viewing audit logs). The target database's privileges remain the final enforcer for data access.
- **SEC-TGT-062** — Privilege checks that DBLoom performs on behalf of the UI shall check the privilege that is actually required. *Replaces:* `isSuperUser()` meaning only "can read `mysql.user`" (SEC-SAU-322).

## 8. Output, files and imports

- **SEC-TGT-070** — All HTML output shall be produced by templates with contextual auto-escaping, and any raw output shall be explicitly marked and reviewed.
- **SEC-TGT-071** — File upload and import shall enforce size limits, decompression-size and ratio limits, an allow-list of types, random temporary names and no use of client-supplied paths. Reading files from the server filesystem shall be off by default and shall be enabled only in `.env`, with the directory fixed there; server-side saving of exports is not provided. *(changed, owner decisions D-17)*
- **SEC-TGT-072** — Exported file names shall be derived safely from sanitised input, and the response shall set the content type and `Content-Disposition` explicitly. *Legacy basis:* filename handling in SEC-IOX-033.
- **SEC-TGT-073** — Serialised data from the client or from storage shall not be deserialised with a general-purpose object deserialiser.

## 9. Cryptography and secrets

- **SEC-TGT-080** — Only well-reviewed libraries and primitives shall be used (e.g. libsodium); no custom cryptography. Algorithm and key sizes shall be documented.
- **SEC-TGT-081** — Application secrets shall come from the environment or a secret manager, never from the repository or from a world-readable file, and the application shall refuse to start with a missing or placeholder secret. There is one application master secret (with a key ring for rotation, at least 32 bytes) from which purpose-bound keys for CSRF, signed client state (SEC-TGT-118) and encryption of reversible fields are derived; there is no separate session secret, because sessions are server-side. Startup verifies the key against a canary record. *(changed, owner decisions D-01 to D-23 accepted, C-16)* *Replaces:* legacy `blowfish_secret` handling (see 01-configuration.md).
- **SEC-TGT-082** — Where DBLoom keeps data that needs integrity protection (for example signed request parameters), it shall use keyed MACs with constant-time comparison.

## 10. Audit, operations and supply chain

- **NFR-TGT-090** — An audit log shall record logins and failures, 2FA changes, connections to targets (host, user, outcome), configuration changes and destructive statements, without secrets or result data. Audit retention shall be an administrator setting within an `.env` floor and ceiling (PROPOSED, unverified: 90 to 1095 days, default 365); there shall be no UI function to delete or edit entries; access shall be limited to the administration plane (SEC-TGT-147), except that ordinary users may see their own events; export shall need step-up and be logged, and an external append-only sink may be configured in `.env`. *(changed, owner decisions D-19)*
- **DEP-TGT-091** — Third-party dependencies shall be pinned with lock files, scanned for known vulnerabilities in CI, and listed in a software bill of materials. Optional security libraries shall not silently change behaviour when absent: a missing library shall disable the feature or fail startup, never fall back to a weaker implementation. *Replaces:* the WebAuthn silent fallback to `CustomServer` (FR-SAU-210).
- **DEP-TGT-092** — Insecure defaults shall be avoided: no default credentials, TLS on, debug and test backends off. *Legacy basis:* the debug-only `simple` 2FA backend (`$cfg['DBG']['simple2fa']`).
- **NFR-TGT-093** — Security-relevant failures shall fail closed. *Replaces:* known fail-open behaviour recorded as defects in `00-overview.md` §6.

## 11. User management (account mode only)

*Decision CF-011: the first administrator is also the first user; users are created only by an administrator entering username and password, or by invite link. Registration with approval and open registration are excluded. In direct mode there are no DBLoom users and this section does not apply. Items marked "proposed detail" go beyond the decision and are not yet approved.*

- **DEP-TGT-100** — On first deployment the administrator shall choose the login mode and set the password of the first administrator, who is also the first user. After setup completes, the setup function shall be permanently disabled. No default credentials shall exist (DEP-TGT-092). Setup is protected by a one-time token of at least 128 bits, supplied by environment variable or generated at startup and stored only as a hash; a generated token is printed to the console (standard output) at startup while setup is pending and is also written to a file readable only by the DBLoom user; a new token is generated at each start until setup completes; it is valid for 60 minutes from process start and single use; when setup completes DBLoom prints a "setup token consumed" message and discards the token; a CLI command shows a pending token on the host. The deployment guide shall state that the token appears in the console output while setup is pending. This is the single exception to SEC-TGT-023. This keeps whoever reaches a fresh installation first from taking it over. The first administrator enrols a factor before setup completes (SEC-TGT-014). *(changed, owner decisions D-04 revised to "setup token on console allowed, option 2", D-07)*
- **FR-TGT-101** — Accounts shall be created only (1) by an administrator, or (2) by invite link. DBLoom shall provide no self-registration, neither with approval nor open (decision CF-011).
- **FR-TGT-102** — An administrator shall be able to create a user by entering a username, an initial password and a role.
- **SEC-TGT-103** — Passwords shall be stored hashed (SEC-TGT-015) and shall never be displayed again after creation. A password set by an administrator is temporary and the user shall be required to change it at first login (decided, CF-011). 2FA enrolment shall follow policy (SEC-TGT-014).
- **FR-TGT-104** — An administrator shall be able to create an invite link that assigns a role. The link shall be single-use, expire, be revocable, and be stored only as a hash. The invited user shall set their own credentials (passkey or password) when using it. DBLoom shall display the link to the administrator for manual hand-over; DBLoom shall not send email (decided, CF-011). *Proposed detail:* tokens of at least 128 bits of randomness, default lifetime 7 days (configurable), optionally bound to an email address. Issuing the link requires step-up (SEC-TGT-143). Invites for the administrator role are treated like recovery (FR-TGT-105). Lifetimes are administrator settings within `.env` bounds. Token strength is 256 bit (minimum 128, PROPOSED). *(changed, owner decisions D-05, D-09)*
- **FR-TGT-105** — An administrator shall be able to disable, delete and change the role of users, and to start credential recovery for a user by issuing a new invite-style link, which the administrator hands over manually (no email; decided, CF-011). The last remaining administrator shall not be deletable, disableable or demotable. Recovery shall not reveal whether an account exists to an unauthenticated visitor. Issuing the recovery link requires step-up (SEC-TGT-143). Redeeming it resets the password, revokes all passkeys and TOTP of the user, forces re-enrolment, revokes the user's sessions, does not affect the vault (SEC-TGT-026) and creates an in-app notice for the user and the administrators (FR-TGT-149). Lifetimes are administrator settings within `.env` bounds. Recovery of an administrator account by CLI on the host only is an optional hardening, not required. *(changed, owner decisions D-05)*
- **SEC-TGT-106** — *(Applies once shared profiles exist; deferred, FUTURE.md FU-005.)* A newly created user shall have no access to any shared connection profile (SEC-TGT-025) until an administrator grants it.
- **NFR-TGT-107** — User creation, invitation, role change, disabling, deletion and recovery shall be recorded in the audit log (NFR-TGT-090).

## 12. Web application hardening

*DBLoom is a web-based application, like LegacyAdmin (decision, project owner). Inbound exposure (who may reach DBLoom, transport security, proxies) is covered by research in section 13.*

- **SEC-TGT-110** — DBLoom shall be delivered as a web application. It shall not reuse LegacyAdmin code or PHP; the technology stack is likely TypeScript with TanStack (owner statement, tentative, see `OPEN.md` item 2). Legacy requirements that are PHP-specific (PHP version and extensions, Composer, php.ini, PHP session handling) describe the legacy implementation and do not carry over. All requirements in this file about sessions, cookies, headers and request handling apply to it.
- **SEC-TGT-111** — The server shall never trust state sent back by the client. Session state shall be kept server-side. Any state that must travel through the browser (hidden fields, URL parameters, cookies) shall be integrity-protected with a keyed MAC bound to the session and to the purpose of that value, and shall also be validated on receipt. Identifiers supplied by the client (database, table, column and route names, sort fields) shall be validated server-side against the schema the server knows or against an allow-list. The layers that implement this are SEC-TGT-114 to 119. TLS protects the transport and does not replace these checks, because the client itself is under the user's control. *Legacy basis:* values round-tripped through requests and re-interpolated into queries (SEC-SAU-319, 320, 323).
- **SEC-TGT-112** — All data read from a target server is untrusted: cell values, database, table and column names and comments, routine and trigger bodies, and error messages. It shall be encoded for its output context (HTML text, HTML attribute, JavaScript, URL) by auto-escaping templates. Cell values shall be displayed as text; DBLoom shall not render database content as HTML. If a display mode that interprets content (for example as a link or image) is offered, it shall pass a sanitiser and remain subject to the content security policy (SEC-TGT-043). Client-side code shall insert data as text, never as HTML. Data embedded as JSON in a page shall be encoded so it cannot close the surrounding script or attribute. Exports to spreadsheet formats shall neutralise cells that start with `=`, `+`, `-`, `@`, TAB or CR (formula injection), unless the user disables it for one export and the administrator policy permits that. *(changed, owner decisions D-16)* *Legacy basis:* the transformation/display plugins and the XSS defects recorded in `05-security-auth.md` §12.1.
- **SEC-TGT-113** — DBLoom shall not load or execute code selected by a request-supplied name (no dynamic include, no class or file loaded from user input). Import and export formats and display transformations shall be built-in modules selected from a closed, fixed registry. A plugin system for third-party extensions is not part of the first release (`FUTURE.md` FU-006; interpretation of the owner's statement, to be confirmed). *Legacy basis:* file-inclusion defects of the transformation and plugin loading described in `06-plugins.md`.

**Untrusted client state (SEC-TGT-111) in detail.** SEC-TGT-111 states the principle; SEC-TGT-114 to 119 are the layers that implement it (PROPOSED, from the review discussion; to be confirmed by the owner). Example from the legacy system: the binary-log page sends `log=<file name>` in the request and the server concatenates it into `SHOW BINLOG EVENTS IN '...'` (SEC-SAU-319); the same pattern occurs for the zoom-search plot limit (SEC-SAU-320) and the process-list sort order (SEC-SAU-323).

- **SEC-TGT-114** — Server-side state first. State that the server can hold (current selection, filters, wizard progress, query being edited) shall be kept in the server-side session. The browser shall carry only opaque identifiers or indexes that refer to it, not names, SQL fragments or file paths. *Verification:* for each page, a request that changes the identifier to one the session does not hold is rejected; no endpoint accepts a free-text name where an identifier would do.
- **SEC-TGT-115** — Boundary validation by schema. Every request handler shall declare a schema for its input (type, range, length, allowed values, pattern) and validate against it before any use. Invalid input shall be rejected with an error, never silently corrected. Numeric parameters (limits, offsets, page sizes) shall be integers within a stated maximum; sort and column fields shall come from a fixed list. *Verification:* automated tests send oversize, wrong-type, out-of-list and malformed values to every endpoint and expect a rejection; a check fails the build if a handler has no input schema.
- **SEC-TGT-116** — Identifiers checked against the server's knowledge. Database, table, column, routine, log and file names received from the client shall be accepted only if they exist in the schema or list that the server holds for that connection (for example the result of `SHOW BINARY LOGS` for a log name), and only then be quoted by the central function (SEC-TGT-051). *Verification:* a test requests a well-formed name that does not exist and expects rejection before any query is sent.
- **SEC-TGT-117** — No string-built SQL outside the central builder. Values shall use parameterised queries and identifiers the central quoting function (SEC-TGT-051). The build shall include a static-analysis or lint rule that rejects SQL assembled by concatenation or interpolation anywhere else. *Verification:* the rule is part of CI and a deliberately injected concatenation makes the build fail.
- **SEC-TGT-118** — Signed client-carried state. Where state must pass through the browser (for example a pagination cursor or a wizard step), it shall carry a keyed MAC computed over the value, the session, the user, the purpose and an expiry. A missing, changed, reused-for-another-purpose or expired token shall be rejected. A valid token shall still go through SEC-TGT-115 and 116. *Verification:* tests alter one byte of a token, replay it in another session and for another purpose, and let it expire, and expect rejection each time.
- **SEC-TGT-119** — Authorisation and regression tests. Authorisation shall be checked again on every request (SEC-TGT-060); a later step shall not inherit trust from an earlier one. The legacy defects SEC-SAU-319, 320 and 323 shall be turned into regression tests that fail if the behaviour of the old implementation (accepting the raw value) is reproduced. *Verification:* the regression tests exist and run in CI.

*Note on the technology stack:* if the TypeScript/TanStack stack is chosen (tentative), SEC-TGT-115 is typically met with a schema validation library on each server endpoint; the exact framework mechanism is to be verified when the stack is fixed.

## 13. Inbound exposure

*Who may reach DBLoom and how. All items are **PROPOSED** (not approved). Basis: `reviews/research-inbound-exposure.md` (sources, legacy evidence and unverified points are listed there; "Source" lines name only the main reference). Legacy paths are relative to the LegacyAdmin 5.2.3 tree. Items that depend on the unconfirmed stack (TypeScript/TanStack, `OPEN.md` item 2) say what must be verified.*

### 13.1 Transport and listening

- **SEC-TGT-120** — **PROPOSED.** DBLoom shall not serve authentication, session or application traffic over plain HTTP to non-loopback peers. Either DBLoom terminates TLS itself, or it runs behind a declared TLS-terminating reverse proxy (SEC-TGT-127). Credentials shall never be accepted on a plain-HTTP request except from a loopback peer on a loopback bind. *Legacy basis:* none; `ForceSSL` does not exist in 5.2.3 and HTTPS is only detected (`libraries/classes/Config.php:788-824`). *Source:* OWASP TLS Cheat Sheet, https://cheatsheetseries.owasp.org/cheatsheets/Transport_Layer_Security_Cheat_Sheet.html (verified). *Verification:* integration test sends a login POST over HTTP from a non-loopback address and expects refusal or redirect without processing the body; check that the Node/runtime adapter can terminate TLS (to be verified).
- **SEC-TGT-121** — **PROPOSED.** Minimum TLS version 1.2, TLS 1.3 preferred; TLS 1.0/1.1 and SSL disabled; cipher suites and certificate key sizes follow a named current profile (Mozilla/tlsref Intermediate or stricter), documented with its version. Whether to require TLS 1.3 only is an open decision. *Legacy basis:* none (delegated to the web server). *Source:* OWASP TLS Cheat Sheet (verified); Mozilla Server Side TLS successor https://docs.tlsref.org/ and NIST SP 800-52r2 https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-52r2.pdf (profile contents NOT verified). *Verification:* scan the listener with a TLS scanner (for example testssl.sh) in CI against the documented profile; a TLS 1.1 handshake must fail.
- **SEC-TGT-122** — **PROPOSED.** When plain HTTP is accepted at all (port 80 listener), it shall only answer `GET`/`HEAD` with a permanent redirect (301 or 308) to the configured public HTTPS origin, built from configuration and never from the request `Host`; all other methods shall be rejected with no side effects. *Legacy basis:* none. *Source:* OWASP TLS Cheat Sheet (verified). *Verification:* test with a forged `Host` header; the `Location` shall still point at the configured origin.
- **SEC-TGT-123** — **PROPOSED.** Over HTTPS DBLoom shall send `Strict-Transport-Security` on every response, default `max-age` of at least 31536000 s (the OWASP example uses 63072000), `includeSubDomains` configurable, `preload` off by default and documented as practically irreversible; the documentation shall recommend a short `max-age` during first rollout. When TLS is terminated by a proxy, either DBLoom or the proxy shall set the header and the deployment guide shall say which (SEC-TGT-043 lists HSTS "where served over HTTPS"). *Legacy basis:* no HSTS in `libraries/classes/Header.php:486-538`. *Source:* OWASP HSTS Cheat Sheet, https://cheatsheetseries.owasp.org/cheatsheets/HTTP_Strict_Transport_Security_Cheat_Sheet.html (verified). *Verification:* response-header test over TLS; no HSTS over plain HTTP; verify that the header can be set centrally for SSR pages, server functions and server routes in the chosen framework (to be verified).
- **SEC-TGT-124** — **PROPOSED.** The default listen address shall be loopback (`127.0.0.1` and `::1`). Binding to any non-loopback address shall require an explicit setting and, together with it, a configured public origin (SEC-TGT-126) and either DBLoom TLS or a declared trusted proxy; otherwise DBLoom shall refuse to start with a message naming the missing setting. *Legacy basis:* none (PHP has no listener). *Source:* general secure-default practice; not tied to a verified document. *Verification:* start with `0.0.0.0` and no TLS/proxy/origin and expect exit with error; confirm the default bind of the chosen Node/Nitro output and how host/port are configured (to be verified).
- **SEC-TGT-125** — **PROPOSED.** When DBLoom is configured to be reachable beyond loopback, it shall show a persistent warning to administrators (and log at startup) if any of these hold: no enforced 2FA (SEC-TGT-014), no effective IP allow-list (computed from the `.env` outer allow ceiling and the UI list; the default ceiling is public, so with no narrower list this trigger holds) and no mTLS, direct mode enabled (SEC-TGT-018), HSTS disabled, TLS certificate verification to targets disabled, a debug flag or debug log level, setup still open, any outbound feature enabled, a high-risk module enabled, or a probe allow-list wider than loopback. Wildcard allowed hosts are refused on non-loopback binds (SEC-TGT-126) and therefore no longer a warning trigger. The administration plane is restricted separately (SEC-TGT-147), so a public outer ceiling does not expose administrative functions. The warning shall not block use unless the owner decides otherwise (open decision). *(changed, owner decisions D-02, D-12, D-13, D-14, D-17)* *Legacy basis:* none. *Source:* project analysis, `reviews/research-inbound-exposure.md` section 4.8. *Verification:* UI and log test for each trigger.

### 13.2 Host, proxy and client address

- **SEC-TGT-126** — **PROPOSED.** The deployment shall configure a public origin (scheme, host, optional port) and a list of allowed host names. Requests whose `Host` is not in the list shall be rejected (421 or 400) without echoing the value. A wildcard in the list shall be refused at startup on a non-loopback bind. *(changed, owner decisions D-13)* Absolute URLs, redirects, invite and recovery links, the cookie `Secure` decision and the WebAuthn RP ID/origin shall be built from the configured public origin and never from request headers. *Legacy basis:* `HTTP_HOST` is used unvalidated in titles, export file names and the 2FA relying-party host (`libraries/classes/Util.php:1628,1653`; `libraries/classes/Plugins/TwoFactorPlugin.php:165-169`; `libraries/classes/Controllers/Preferences/ManageController.php:80,91`). *Source:* OWASP WSTG host header injection test, https://owasp.org/www-project-web-security-testing-guide/latest/4-Web_Application_Security_Testing/07-Input_Validation_Testing/17-Testing_for_Host_Header_Injection (search summary only; no dedicated cheat sheet found). *Verification:* tests with forged `Host`, `X-Forwarded-Host` and `Forwarded` headers; an invite link in the response must still use the configured origin.
- **SEC-TGT-127** — **PROPOSED.** Forwarded headers (`X-Forwarded-For/Proto/Host`, `Forwarded`) shall be ignored unless the immediate TCP peer is in a configured trusted-proxy list (IPv4 and IPv6 CIDR; default empty). For a trusted peer the effective client address shall be the rightmost entry of the combined ordered list of all forwarded-for values that is not itself a trusted proxy (or the entry selected by a configured hop count), never the leftmost; malformed values shall make the address "unknown". Scheme and host from forwarded headers may only confirm, never override, the configured public origin. One module shall compute the effective client address, scheme and host; no other code shall read forwarded headers. The deployment guide shall state that the proxy must overwrite inbound `X-Forwarded-*` headers and that the application port must be unreachable except through the proxy. *Legacy basis:* `TrustedProxies` is an exact-IP map with no CIDR and reads only the first (leftmost) value (`libraries/classes/Core.php:806-840`; `libraries/config.default.php:2842-2844`); `isHttps()` trusts about ten scheme headers from any client (`libraries/classes/Config.php:799-818`). *Source:* MDN X-Forwarded-For, https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/X-Forwarded-For (verified); OWASP CSRF Cheat Sheet proxy section (verified). *Verification:* tests with spoofed `X-Forwarded-For` from an untrusted peer, multiple header lines, chained proxies and IPv4-mapped IPv6; check whether the runtime (h3/Nitro) does its own forwarded-header handling (to be verified; an old h3 issue says it has no trust notion).
- **SEC-TGT-128** — **PROPOSED.** IP allow/deny lists shall be an optional global setting, expressed in CIDR notation for IPv4 and IPv6 (single addresses as /32 and /128), parsed and matched by a maintained library or runtime facility with IPv4-mapped IPv6 normalisation; invalid rules shall stop startup; an unknown client address shall be denied when a list is configured. The IPv4 prefix-matching defect of the legacy matcher (SEC-SAU-303) shall not be reproduced: `10.0.0.0/8` shall not match `138.1.2.3`. There shall be an outer allow ceiling and a permanent deny list for inbound addresses, set in `.env` only (the UI list can only narrow within the ceiling). The default of the outer allow ceiling is PUBLIC (no network restriction by default); administrators may narrow it. A public default does not make the administration plane public: administrative functions are restricted separately to the administration networks (SEC-TGT-147, default loopback), and the loopback default bind of SEC-TGT-124 is unchanged. Per-user address rules are not in scope; rules apply to roles only. The evaluation model (legacy orderings versus one allow-then-deny model) is an open decision. *(changed, owner decisions D-02, D-03)* *Legacy basis:* `libraries/classes/IpAllowDeny.php:67-107` (mask built from bits 30..0, bit 31 ignored); `libraries/classes/Plugins/AuthenticationPlugin.php:272-309`; spec SEC-SAU-302 and SEC-SAU-303 in `05-security-auth.md`. *Source:* MDN XFF for the trust rule (verified); library choice not researched. *Verification:* unit tests including the legacy vector, prefix lengths 0, 1, 8, 24, 31, 32 and IPv6 0, 64, 128; fuzz test of rule parsing.
- **SEC-TGT-129** — **PROPOSED.** The network restrictions (allow/deny list, allowed hosts, mTLS check) shall run as global middleware before routing and authentication, covering every route class: pages, static assets, server functions, server routes, setup and health endpoints. Before the store is open, or when it cannot be read, the middleware shall evaluate `.env` rules only and shall never run with no policy. The probe allow-list for health checks is set in `.env`. *(changed, owner decisions D-12)* *Legacy basis:* AllowDeny runs only inside the authentication step (`libraries/classes/Plugins/AuthenticationPlugin.php:272-309`) and `setup/` has no check. *Source:* project analysis (SEC-TGT-060 deny-by-default). *Verification:* a route-inventory test enumerates all registered routes and asserts each is denied from a disallowed address; confirm that the framework allows one middleware that covers server functions and server routes alike (to be verified).
- **SEC-TGT-130** — **PROPOSED, optional feature.** Mutual TLS may be offered in two forms: client-certificate verification by DBLoom against a configured CA, or a certificate identity passed by a trusted proxy in a header accepted only from trusted peers. mTLS gates network access and does not replace DBLoom authentication unless the owner later decides otherwise. *Legacy basis:* none. *Source:* OWASP TLS Cheat Sheet, mTLS section (verified). *Verification:* tests with no certificate, an expired one, a wrong CA, and a forged identity header from an untrusted peer.

### 13.3 Rate limiting, endpoints, browsers

- **SEC-TGT-131** — **PROPOSED.** Application-level rate limiting (SEC-TGT-017) shall be always on and shall not depend on an edge component; it shall key on the effective client address from SEC-TGT-127 and, independently, on the account. Edge (proxy, WAF, CDN) limits are recommended in the deployment guide and shall never be assumed. DBLoom shall also enforce request body size, header size and concurrent-connection limits. The scope of the limit store (per instance or shared) shall be documented. *Legacy basis:* no brute-force protection (SEC-SAU-206). *Source:* MDN XFF (rate limiting only on trusted addresses; verified). *Verification:* rotating a spoofed `X-Forwarded-For` from an untrusted peer does not reset the limit; one attacker behind a proxy does not lock out all users when the real address is available.
- **SEC-TGT-132** — **PROPOSED.** Health and diagnostic endpoints: one unauthenticated liveness endpoint may exist, returning a fixed minimal body with no version, configuration or dependency detail, subject to the network restrictions and rate limits, with its own probe allow-list in `.env` (default loopback; probes come from outside user ranges). *(changed, owner decisions D-12)* Readiness detail, metrics, version and any debug or diagnostic page shall require an administrator session or a loopback peer, shall be off in production builds where they are debug-only, and shall return `Cache-Control: no-store`. *Legacy basis:* none (no health endpoint). *Source:* project analysis. *Verification:* an unauthenticated request to every diagnostic route returns 401, 403 or 404 with no version string; scan responses for version disclosure.
- **SEC-TGT-133** — **PROPOSED.** CORS shall be disabled by default: no `Access-Control-Allow-*` header is sent. If cross-origin use is ever enabled it shall use an exact-origin allow-list, never `*` together with credentials, never reflect the `Origin` value, and never allow `null`. *Legacy basis:* no CORS headers anywhere in the PHP code (search for `Access-Control` finds none). *Source:* OWASP CSRF Cheat Sheet, https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html (verified). *Verification:* preflight and simple cross-origin requests from an unlisted origin receive no CORS headers.
- **SEC-TGT-134** — **PROPOSED.** State-changing requests shall be checked against the configured public origin using `Sec-Fetch-Site`, `Origin` and `Referer` (exact origin match; missing or `null` rejected), in addition to the CSRF token of SEC-TGT-042. This check shall cover server functions and any server route or plain HTTP endpoint. The framework's CSRF middleware shall not be bypassed, its origin shall be set from configuration, and the opt-out for missing headers shall be off. *Legacy basis:* POST-only token check (SEC-SAU-324). *Source:* OWASP CSRF Cheat Sheet (verified); TanStack Start server functions guide, https://tanstack.com/start/latest/docs/framework/react/guide/server-functions (verified; server-route coverage is stated only by a third-party guide and is not verified). *Verification:* a cross-site POST to each server function and server route is rejected; a same-origin request through a proxy that rewrites `Host` succeeds; confirm behaviour for the pinned TanStack Start version (to be verified).
- **SEC-TGT-135** — **PROPOSED.** Cookies and caching behind proxies: the `Secure` flag shall follow the configured public scheme, not request headers; state-changing server functions shall use POST; no response that depends on identity shall be cacheable by shared caches. Deployment under a URL sub-path is not supported in the first release (DBLoom is served at the root of a host name; the `__Host-` prefix of SEC-TGT-040 needs path `/`). *(changed, owner decisions D-11)* *Legacy basis:* `Secure` follows `isHttps()` (`libraries/classes/Config.php:974`); cookie names get `__Secure-` and `_https` (`Config.php:1009`); `SameSite=Strict` default (`libraries/config.default.php:802`). *Source:* OWASP CSRF Cheat Sheet, SameSite section (verified); TanStack guide on caching (verified); the `__Host-` prefix rule is NOT verified in this research. *Verification:* cookie test behind a TLS-terminating proxy with and without `X-Forwarded-Proto`; browser test for `__Host-` on each supported deployment shape.
- **SEC-TGT-136** — **PROPOSED.** Every server function and server route shall be listed in a registry that declares its authentication and authorisation requirement; a build or test step shall fail if an endpoint exists that is not in the registry or is declared public without justification. Authentication shall be enforced inside the handler or in mandatory middleware, not only in route guards. *Legacy basis:* no router-level authorisation (SEC-SAU-321). *Source:* TanStack Start docs (authentication inside the server function; verified). *Verification:* registry-versus-build-output comparison test; check how the framework exposes generated function IDs and URLs (to be verified).
- **SEC-TGT-137** — **PROPOSED.** Responses shall carry `X-Robots-Tag: noindex, nofollow`, and authenticated pages shall be served with no-store caching headers. *Legacy basis:* `libraries/classes/Header.php:528,530`. *Source:* legacy code. *Verification:* header test.

### 13.4 Deployment and operations

- **DEP-TGT-120** — **PROPOSED.** The deployment guide shall define supported topologies in order of preference: (1) loopback bind plus SSH tunnel or VPN, (2) private network behind a TLS reverse proxy with IP allow-list, (3) internet-facing behind a TLS proxy with mTLS or an identity-aware proxy and enforced 2FA, (4) direct TLS on the internet (discouraged). For each it shall state where TLS ends, the bind address, the trusted-proxy setting, which headers the proxy must overwrite, and which warnings DBLoom will show. Remote administration requires an administration range in `.env` (SEC-TGT-147). Edge-runtime or serverless hosting shall be stated as supported or unsupported once the owner decides (open). *Legacy basis:* none (legacy relied on web-server configuration). *Source:* `reviews/research-inbound-exposure.md` section 4.8. *Verification:* documentation review; each topology exercised in the integration test environment.
- **DEP-TGT-121** — **PROPOSED.** Reference configurations for at least one common reverse proxy shall be provided and tested in CI (TLS settings, HSTS, header overwrite, timeouts, body size, rate limit). For containers the guide shall state that the process may bind `0.0.0.0` inside the container while the published port should be bound to loopback unless exposure is intended. *Legacy basis:* none. *Source:* project analysis; OWASP CSRF Cheat Sheet on proxy header stripping (verified). *Verification:* a CI job runs the reference proxy in front of DBLoom and executes the SEC-TGT-122, 123, 126 and 127 tests through it.
- **DEP-TGT-122** — **PROPOSED.** At startup, and on demand through a command-line check, DBLoom shall print an exposure report (bind address, TLS state and version, public origin, allowed hosts, trusted proxies, allow/deny lists, mTLS, enabled diagnostic endpoints, login mode, 2FA policy) and the warnings of SEC-TGT-125, without secrets. *Legacy basis:* none. *Source:* project analysis. *Verification:* snapshot test of the report for each topology.
- **DEP-TGT-123** — **DECIDED (owner, option 2), extends DEP-TGT-100.** The first-run setup function shall be reachable from any address that can reach DBLoom, as in WordPress, so that the administrator can complete setup immediately after deployment from any machine. Setup shall be protected by the one-time token of DEP-TGT-100 and nothing else is required to reach it; a request without the correct token shall not progress and shall not reveal whether setup is pending beyond what the setup page itself shows. The default bind address remains loopback (SEC-TGT-124), so the deployer sets the bind address in `.env` to make DBLoom reachable, which the deployment guide shall state. Attempts with a wrong token shall be rate-limited (SEC-TGT-017). After setup the routes shall return 404. *(changed, owner decisions D-04 revised: the loopback-only restriction of the earlier proposal is dropped)* *Legacy basis:* `setup/index.php` and `setup/config.php` contain no source-address check; protection relies on the file-system layout of the config directory. *Source:* project analysis; DEP-TGT-100. *Verification:* test setup from loopback, from a remote address, and from loopback via a local proxy with `X-Forwarded-For`; test that setup returns 404 after completion.
- **NFR-TGT-120** — **PROPOSED.** An automated test suite shall run DBLoom behind a real proxy and also directly, covering spoofed forwarded headers, forged `Host`, direct access to the application port, missing `Origin`, and redirect behaviour; its results are part of the evidence for SEC-TGT-001. *Legacy basis:* none. *Source:* ASVS evidence principle (secondary source only; ASVS 5.0 requirement numbers not verified). *Verification:* the suite exists in CI and fails on regression.
- **NFR-TGT-121** — **PROPOSED.** The TLS configuration, security headers and exposure report shall be re-verified on every release and after each framework upgrade, because proxies, adapters or framework updates can silently drop headers. *Legacy basis:* none. *Source:* Report URI note on ASVS headers (secondary). *Verification:* release checklist item with a header-diff test.
- **NFR-TGT-122** — **PROPOSED.** The "to be verified" items (runtime bind and trusted-proxy behaviour, TanStack server-route CSRF coverage, chosen CIDR library behaviour, `__Host-` prefix handling, ASVS version and requirement numbers, current TLS profile text) shall be closed before the requirements of this section are approved. *Legacy basis:* none. *Source:* `reviews/research-inbound-exposure.md` section 5. *Verification:* each item has a recorded result linked from the research file.

## 14. Deployment configuration and administrator settings

*Decided (project owner): deployment settings are configured through `.env`; administrator settings are configured from the UI. The five rules and the three additional measures below were accepted in discussion ("sounds good"). Items marked "proposed detail" go beyond that and are not yet approved. Later the owner accepted the recommendations D-01 to D-23 of `12-settings.md` section 6 with the change that the inbound outer allow ceiling is public by default (D-02); D-08 (passkey as primary credential or only second factor; TOTP in the first release) is not decided. Requirements changed by these decisions are marked "(changed, owner decisions D-nn)". All numeric floors, defaults and ceilings remain PROPOSED and unverified.*

*Scope: the administrator UI exists in account mode only, because direct mode has no DBLoom users or administrators (CF-009). In direct mode the settings in this section come from `.env` alone. (Consequence drawn by the reviewing engineer; confirmed by the owner.)*

- **DEP-TGT-140** — Deployment configuration shall be supplied through a `.env` file and/or process environment variables and applied at startup. It covers at least: bind address and ports, TLS mode, certificates, public origin, allowed host names, trusted proxies, HSTS, mTLS, CORS, CSP settings, listener limits and timeouts (SEC-TGT-124 to 127, 131); the login mode (SEC-TGT-019); first-run setup rules and setup token; the location and credentials of the DBLoom store; the application master secret and key ring (SEC-TGT-081); log destinations, audit sink and debug flags; the log level (raising it is not offered in the UI); outbound proxy and permits for outbound features (version check, default off); health and diagnostic endpoints; temporary and cache directories; administration networks (SEC-TGT-147); the outer allow ceiling (default public, D-02) and permanent deny list for inbound addresses; target hard blocks, TLS-to-target floors, certificate-verification permit and extra CA; Argon2id parameters, TOTP window and WebAuthn relying-party ID; step-up window, auto-revert period and loosening delay; and every floor, ceiling, envelope, permit flag and lock of the settings in FR-TGT-141 (SEC-TGT-142). Error reporting to third parties, telemetry, captcha, server-side export saving and the master key for shared profiles are not provided. The complete classification is `12-settings.md`. The `.env` file shall not be committed to version control, not be served over HTTP, and be readable only by the DBLoom process user. Missing or placeholder required values shall stop startup (SEC-TGT-081). *Proposed detail:* real environment variables take precedence over `.env`. *Verification:* a test starts DBLoom with a missing required value and with a placeholder and expects a refusal; a request for `/.env` returns 404. *(changed, owner decisions D-01 to D-23 accepted (C-04); D-02, D-12, D-14, D-17, D-20)*
- **FR-TGT-141** — Administrators shall be able to change the administrator settings classified "UI within ENV bounds" in `12-settings.md` from the UI; values are stored in the DBLoom store. They include at least: IP allow/deny lists (SEC-TGT-128, within the outer allow ceiling), enforced-2FA scope and grace period (SEC-TGT-014), session lifetimes (SEC-TGT-041), login throttling (SEC-TGT-017, 131), the target-host policy within its `.env` envelope (SEC-TGT-030), invite and recovery link lifetimes (FR-TGT-104, 105), password policy within its floors, audit retention, notice thresholds (FR-TGT-149), query and size limits, and import/export module selection. Settings of DEP-TGT-140 shall not be editable from the UI, so that a stolen administrator session cannot widen exposure, and a direct API call to change one shall be rejected. Importing settings (if offered, CLI only) shall pass the same limits. In direct mode the same settings come from `.env`. The effective value of each setting follows the precedence rule (SEC-TGT-150). The allowed second factors (passkey, TOTP; recovery codes always allowed) are administrator settings that may be narrowed within the factors enabled in `.env` and never widened beyond them; at least one factor shall remain enabled (ST-056). The allowed primary credential is not listed here because it depends on the open second half of D-08. *Verification:* the settings page offers no field for a `.env`-only setting, and a direct API call to change one is rejected. *(changed, owner decisions D-01, D-20, D-08 first half)*
- **SEC-TGT-142** — Bounded by `.env`. The deployment configuration shall define, for each administrator setting, a floor and ceiling (numbers), an envelope (lists) or a permit and a force flag (booleans), and may lock the setting. The UI may move a value inside these limits, in both directions, and the server shall reject values outside them on write and clamp them on read, with a warning and an audit entry. *Verification:* a request that sets a session lifetime above the ceiling is rejected; a stored value above a later-lowered ceiling is clamped on read. *(changed, owner decisions D-01)*
- **SEC-TGT-143** — Step-up check. Changing a setting classified "UI within ENV bounds" or a user-management action (role change, invite or recovery link, disable, delete) shall require a fresh passkey or 2FA confirmation within the step-up window (`.env`, PROPOSED default 5 minutes), even in an active session. Administrator accounts always have 2FA (SEC-TGT-014). A change that loosens a setting may additionally be held pending for a cooling-off period (`.env`, default 0 = immediate), shown as pending and cancellable. Automatic revert (SEC-TGT-144) needs no step-up. *Verification:* a settings change from a session whose last confirmation is older than the configured step-up window is refused until the user confirms again; a pending loosening takes effect only after the delay. *(changed, owner decisions D-01, D-07)*
- **SEC-TGT-144** — Lockout protection. If a change to the IP allow/deny lists, 2FA scope, login throttling or session lifetimes would exclude the acting administrator or, by preview, other users, DBLoom shall warn with the number of affected users and require explicit confirmation; the check shall use the effective client address (SEC-TGT-127). Such changes shall apply with automatic revert after the auto-revert period (`.env`, PROPOSED default 5 minutes, range 1 to 15) unless confirmed from the new configuration or a new session; the pending change and its deadline (absolute time) are kept in the store so a restart neither loses nor makes it permanent. For other settings (for example target-host policy) the administrator shall see an impact preview, settings shall be versioned with one-click rollback, and the CLI reset shall cover them. A command-line or configuration-file reset shall exist for the case in which all administrators are locked out. The rule also covers changes to the allowed second factors: a change that would leave any user without a usable factor shall be refused after the preview (ST-056). *Verification:* a test applies a restricting list that excludes the tester and confirms that it reverts without confirmation; the reset command restores access; a restart during a pending change keeps the deadline. *(changed, owner decisions D-01, D-08 first half)*
- **NFR-TGT-145** — Audit. Every change of an administrator setting shall be logged with the old and the new value and the acting DBLoom user (NFR-TGT-090). Secrets shall be masked. Clamping of a stored value to `.env` limits and every reset to default shall be audited. If the audit entry cannot be written, the change shall be aborted. *Verification:* changing a setting produces one audit entry with both values. *(changed, owner decisions D-01, D-19)*
- **FR-TGT-146** — Visibility. The administrator page shall show the current exposure report (DEP-TGT-122) and the warnings of SEC-TGT-125. *Verification:* the page shows the same values as the command-line report.

- **SEC-TGT-150** — Precedence. **DECIDED** (owner accepted D-01). The effective value of every setting is the first applicable of: (1) `.env` limits (floor, ceiling, envelope, permit flag, lock), which always win; (2) the UI override stored in the DBLoom store (account mode only); (3) the `.env` default; (4) the built-in default. Values outside the `.env` limits shall be clamped on every read, not only on write, with a warning and one audit entry per distinct clamp; stored data is not rewritten silently and the settings page shows "stored X, effective Y". A permit flag or envelope in `.env` is the ceiling; a force flag is the floor. `.env` may lock a setting (shown read-only with source `.env (locked)`). The settings page shall show each value's source, its permitted range and a "reset to default" action (audited, same step-up as a change). If the store is missing, unreadable or not yet created, only layers 1, 3 and 4 apply, and the network middleware runs on `.env` rules alone (SEC-TGT-129). In direct mode layer 2 does not exist. A change of an `.env` default does not change an existing UI override; a change of an `.env` limit does (by clamping). *Verification:* a stored value outside a later-tightened limit is reported as clamped and audited once; with the store unreadable the middleware still enforces the `.env` rules. *(new, owner decisions D-01)*

Excluded (owner decision): approval of every settings change by a second administrator (four-eyes) is not needed.
